# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tales is a single-binary integration / E2E testing tool (Go 1.26). Tests are written as declarative HCL2 files with the `.tales` extension and executed by the `tales` CLI. Inspired by Robot Framework and Karate, focused on HTTP API workflows with deterministic, seedable test data generation.

## Common Commands

```bash
make build           # Build tales + mockserver into ./build
make test            # Unit tests with -race -count=1 across ./internal/... and ./cmd/tales
make lint            # golangci-lint (config in .golangci.yml, v2 schema)
make e2e             # Build + start mock server + run ./e2e/pass with --seed 1234 --parallel 4
make e2e-failure     # Run ./e2e/fail and assert CLI exits with code 1
make install         # Install tales binary to $GOBIN / $GOPATH/bin
make install-skill   # Copy .claude/skills/tales-test-generator to ~/.claude/skills
```

Run a single Go test:

```bash
go test -race -run TestName ./internal/runtime
```

Run the CLI directly during development:

```bash
go run ./cmd/tales test ./e2e/pass --seed 1234
go run ./cmd/tales validate ./e2e/pass/blog.tales
```

CLI exit codes are load-bearing for CI: `0` pass, `1` failure, `2` parse/validation error, `3` runtime/reporting fatal: match these when adding new exit paths in [internal/cli/test.go](internal/cli/test.go).

## Architecture

Pipeline: HCL files → parser → model → runtime → providers → reporters.

- [cmd/tales/main.go](cmd/tales/main.go): urfave/cli entrypoint, wires `test` and `validate` subcommands. The provider registry built in [internal/cli/test.go](internal/cli/test.go) now includes `load` (HTTP smoke benchmark), `mail` (SMTP/LMTP ingestion), `webhook` (local HTTP receiver), `file` (read-only file inspection) and `exec` (external command runner, gated by `--allow-exec`) alongside `http`, `keyword`, `mobile`, `sql`, `browser`.
- [internal/cli/](internal/cli/): command flags/handlers. `test.go` constructs the provider registry (`http`, `keyword`, `mobile`, `sql`, `mail`, `browser`, `load`, `webhook`, `file`, `exec`) and invokes the runner. `--allow-exec` (urfave `BoolFlag`) is read and passed to `execprovider.WithAllowExec`; without it any `exec` step fails before spawning with `exec provider is disabled by default. Re-run with --allow-exec.` (`tales validate` is parse-only and never reaches the gate). `Options.ProjectDir` is set to `os.Getwd()` and exposed as `project.dir`. `--timeout <duration>` (urfave `DurationFlag`) wraps the runner's input ctx with `context.WithTimeout` before `runner.Run`; downstream providers honor the resulting cancellation through their existing ctx plumbing (HTTP via `NewRequestWithContext`, SQL via `db.QueryContext` / `db.ExecContext`, runtime retry sleeps via `sleepWithContext`). 0 (default) disables the cap. On startup the CLI prints a preflight line (`tales: loaded N scenarios from M files; timeout=...`) on stderr; while the runner is in flight it streams scenario start/end events on stderr via `report.StreamSink` (silenced by `--no-progress`), and when `--verbose` is set a 30s heartbeat lists scenarios still running. When `--timeout` fires before the suite completes, `SuiteResult.StalledScenarios` carries the names of the in-flight scenarios at the deadline moment and the CLI prints them so users know exactly which scenario stalled.
- [internal/parser/](internal/parser/): HCL2 loading. `schema.go` defines the gohcl struct tags that drive the DSL surface; `decode.go` converts those into `model.*`; `loader.go` walks `.tales` files, merges suites, and validates uniqueness of scenario/step/generator/keyword names. **Editing the DSL almost always means changing `schema.go` + `decode.go` together.** Provider-specific decoders (`mail.go`, `sql.go`, `load.go`, `browser.go`, `mobile.go`, `webhook.go`, `file.go`, `exec.go`) follow the `decodeXStepIfNeeded` / `looksLikeXStep` pattern and are dispatched from `decodeProviderSteps` in `decode.go` (`save.go` decodes the http-only `save` block from `decodeSteps`); a step carrying a foreign provider's blocks (e.g. webhook `start`/`wait`/`stop` on a non-webhook provider) is rejected there. gohcl wraps unset optional `hcl.Expression` fields with non-nil zero-range placeholders, so per-field decoders must guard with `exprIsSet` (see `optionalExpr` in `webhook.go`) before populating a `model.Expression`, otherwise `Expression.Empty()` reports false and the runtime evaluates absent fields. `deprecation.go` holds the Go-side deprecation registry (`defaultDeprecations`): `decodeFile` walks every parsed `hclsyntax.Body` via `collectDeprecations`, emitting one `hcl.DiagWarning` (never an error) per deprecated block/attribute occurrence with its source `Subject`. The CLI (`test` + `validate`) surfaces these via `parser.Warnings` + `parser.FormatDeprecation` through `printDeprecationWarnings` ([internal/cli/diagnostics.go](internal/cli/diagnostics.go)) on stderr; warnings never affect the exit code. To deprecate a new element, add one entry to `defaultDeprecations` (block or attribute, optional `within` ancestor-suffix scope) and update the docs/skill. The `case`/`response` aliases are the seeded entries.
- [internal/model/](internal/model/): plain data structures (`Suite`, `Scenario`, `Step`, `Request`, `Expect`, `Keyword`, `Generator`). `Expression` wraps `hcl.Expression` with file/line metadata for diagnostics.
- [internal/lang/](internal/lang/): expression evaluation on top of go-cty. `functions.go` registers built-ins and matchers (matchers are encoded as objects carrying a `__tales_matcher` key, then resolved by the assertion engine). `refs.go` extracts cross-step dependencies (`StepDependencies`) and validates file-order references (`ValidateStepOrder`: rejects forward/unknown `result.<step>` or `depends_on` references). Each provider with `result.*`-bearing expressions needs a `collectXRefs` in **both** `StepDependencies` and `ValidateStepVars` (mobile/sql/webhook/file/exec have one, plus `collectSaveRefs` for the HTTP `save` block; `collectFileRefs` walks `path` + the file expect, `collectExecRefs` walks command/args/env/stdin/timeout/sandbox + the exec expect). Without it a `path = result.<x>.path` or `args = [result.<x>.path]` reference is not ordered, validated, or cascade-skipped. `FindFileRefs` mirrors `FindStepRefs`/`FindVarRefs` for the `file.*` capture namespace.
- [internal/runtime/](internal/runtime/): execution engine.
  - `runner.go` is the orchestrator: scenario-level parallelism via semaphore, then **steps inside each scenario run sequentially in `.tales` file order** (`runScenarioSteps`); a failing step halts the scenario (later steps reported as skipped). Retry loop, teardown is always run after main steps (even on failure).
  - `generator.go` + `seed.go`: deterministic generation. Each `generate()` call mixes (seed, scenario name, keyword call path, step name, generator name, expression path) so identical runs produce identical values regardless of parallelism or retry attempt. The keyword call path is the chain of calling step names (NUL-joined) carried on `lang.Evaluator.seedScope`: it is empty at scenario level (so non-keyword seeds keep their historical formula) and is pushed by `executeKeywordStep` via `evaluator.PushSeedScope(step.Name)` before running the keyword's internal steps + outputs, so the same keyword invoked from different steps (and nested keyword calls) yields distinct values per call site instead of colliding. `seedScope` is mutated single-threaded (one `Evaluator` per scenario, steps run sequentially).
  - `keyword.go` (under provider/keyword): `keyword` blocks are reusable flows with their own inputs/steps/outputs; called via `step "keyword" "name" { name = "...", inputs = {...} }`.
- [internal/assertion/](internal/assertion/): JSON / status / header matcher logic, consuming the matcher objects produced by `lang/functions.go`.
- [internal/provider/](internal/provider/): pluggable execution backends.
  - `http/provider.go`: HTTP provider (including Connect JSON over HTTP). Supports `request.body { json | form | raw }`, `request.auth.basic`. Rejects combining `headers.Authorization` with `auth.basic`. Multipart uploads live in [internal/provider/http/multipart.go](internal/provider/http/multipart.go): `request.body { multipart { file { path|content, field, filename, content_type } | field { name, value } } }`. Parts keep declaration order on the wire, `path` is resolved relative to the `.tales` file owning the step (via `input.Step.File`), and the `Content-Type` header is set automatically with `multipart.Writer.FormDataContentType()`. The four `body` modes (json / form / raw / multipart) are mutually exclusive at decode time.
  - `keyword/`: pseudo-provider that invokes user-defined keyword flows.
  - `sql/provider.go`: SQL provider (`postgres` via [pgx/v5/stdlib](https://github.com/jackc/pgx) + `mysql` via [go-sql-driver/mysql](https://github.com/go-sql-driver/mysql)). Reads `config.sql.connections.<name>.driver/dsn`, opens `*sql.DB` lazily, caches it per-suite, and closes it via the `io.Closer` lifecycle hook. The DSN is augmented with a default dial timeout via [internal/provider/sql/dsn.go](internal/provider/sql/dsn.go) (`timeout=10s` for MySQL, `connect_timeout=10` for Postgres) unless the user already set one, and the first acquire runs a bounded `PingContext` (10s, or sooner if the parent ctx is stricter) so an unreachable database fails fast instead of stalling on the OS TCP retry stack. A failed ping closes the handle and does NOT cache it. Each step declares exactly one of `exec` / `query`; both expose their payload under `response.json` so the existing assertion + capture pipeline works unchanged. DSNs are never copied into reports (only the connection name, driver, SQL text and arg count are). Args are scalar-only (string / number / bool / null), with `int64` precision preserved for bigint primary keys. See [website/src/content/docs/docs/providers/sql.mdx](website/src/content/docs/docs/providers/sql.mdx).
  - `mobile/`: iOS UI provider (V1, `platform = "ios"`). Owns per-target sessions cleaned up at suite end via `Close()` (called by the runner through an `io.Closer` type-assertion). Also implements the `provider.ScenarioHook` capability so a scenario-level `record { }` block produces an MP4 via `xcrun simctl io <UDID> recordVideo`; the recorder is started lazily on the first `acquireSession` (so the simulator is guaranteed booted) and stopped via SIGINT from a defer in `runScenario`. The resolved spec lives in [internal/provider/mobile/scenario_hook.go](internal/provider/mobile/scenario_hook.go); the wrapper around simctl lives in [internal/provider/mobile/apple/simrecord/](internal/provider/mobile/apple/simrecord/) and mirrors the `xcodebuild` Spawner/Process pattern. Subpackages: `driver` (transport-agnostic interface + HTTP/JSON client), `tree` (normalized UI hierarchy + locator), `apple` (`simctl`, `simrecord` recordVideo wrapper, `xcodebuild` launcher, lifecycle facade, target resolver, `embeddeddriver` cache manager). **App launch (`handleLaunch`) and the `terminate {}` step (`finalizeStep`) go through the driver's `/launch` + `/terminate` endpoints (`driver.Driver.Launch`/`Terminate` → `XCUIApplication.launch()`/`terminate()`), NOT `simctl`**: this keeps XCTest's automation session bound to the live app process so scenarios reusing a cached session (same target) each get a working `/hierarchy` snapshot. Launching/terminating out-of-band via `simctl` left XCTest pointing at a dead process and the next scenario's hierarchy fetch timed out (issue #41). `clear_state` uninstall/install, permissions (`simctl privacy`), and the suite-end `Session.Close()` stay on `simctl`. **Driver port**: `config.mobile.targets.<name>.driver.port` is optional in embedded mode; when omitted, `apple.ResolveDriverEndpoint` (in [internal/provider/mobile/apple/port.go](internal/provider/mobile/apple/port.go), called by `appleSessionBuilder` before `EnsureDriver`) auto-allocates a free host port per target — distinct across concurrent targets via a process-wide claimed-port set — so multiple simulators don't collide on the shared loopback. `DriverConfig.PortSet` records an explicit port (honored as-is); external mode never reallocates. **Hierarchy fetch (`/hierarchy`)**: the snapshot runs on a dedicated `snapshotQueue` (off the single HTTP-server queue and the runner main thread) bounded by an 8s timeout + single-flight, returning a retryable `503` when the app under test is momentarily unresponsive (its own main thread busy doing a synchronous refresh) — this stops one stuck `app.snapshot()` from wedging the whole driver and cascading into `POST /tap: EOF` ([Handlers.swift](drivers/apple/TalesAppleDriver/TalesAppleDriverUITests/Handlers.swift)). The tree is encoded from `XCUIElementSnapshot.dictionaryRepresentation` ([Hierarchy.swift](drivers/apple/TalesAppleDriver/TalesAppleDriverUITests/Hierarchy.swift), Maestro-style, more complete than walking the typed `.children`), and `tree.FindByID`/`collectByID` ([internal/provider/mobile/tree/tree.go](internal/provider/mobile/tree/tree.go)) collapse a node + descendant that share one accessibility id — SwiftUI double-encodes a control under a single identifier (e.g. a `.topBarLeading` toolbar item surfaces as both an `other` wrapper and the inner `button`) — to the outermost match instead of failing; two elements in genuinely separate subtrees that share an id still report `ErrDuplicate`. The Swift driver source lives in [drivers/apple/TalesAppleDriver](drivers/apple/TalesAppleDriver) and is embedded into the Tales binary via `go:embed` (see [drivers/apple/embed.go](drivers/apple/embed.go)); at runtime the [internal/provider/mobile/apple/embeddeddriver](internal/provider/mobile/apple/embeddeddriver) package extracts it to `~/Library/Caches/tales/apple-driver/<key>/`, builds it once with `xcodebuild build-for-testing`, then reuses the cached build via `xcodebuild test-without-building`. The cache key includes Xcode version, SDK version, `DEVELOPER_DIR`, iOS simulator runtime, and macOS major. Override the base with `TALES_DRIVER_CACHE_DIR`; wipe with `make clean-ios-driver-cache`. See [website/src/content/docs/docs/providers/mobile-ios.mdx](website/src/content/docs/docs/providers/mobile-ios.mdx).
  - `mail/`: SMTP/LMTP ingestion provider (`step "mail"`, V1). Sends one email per step for test ingestion — it is not a mailbox client. Reads `config.mail.targets.<name>` (smtp: host/port/tls/starttls/auth, lmtp: network tcp|unix/address, common timeout) at runtime from `input.Config` via local cty-navigation helpers in [internal/provider/mail/config.go](internal/provider/mail/config.go) (mirroring sql's `resolveConnection`). The runtime ([internal/runtime/mail.go](internal/runtime/mail.go)) lowers the `message` block into a `provider.MailExecution` and derives a deterministic Message-ID `<hex@tales.local>` from the seed mixer (`DeriveSeed(seed, scenario, step, "message-id")`) unless the user supplies a `Message-ID` header; the seed reaches the step via `ScenarioState.Seed()`. MIME is built with the stdlib in [internal/provider/mail/mime.go](internal/provider/mail/mime.go) (text/plain, text/html, multipart/alternative, multipart/mixed + base64 attachments, CRLF, `mime.QEncoding` subjects, quoted-printable non-ASCII bodies, deterministic boundaries derived from the Message-ID, injectable `now` for byte-exact tests). Transports use [github.com/emersion/go-smtp](https://github.com/emersion/go-smtp) (+ go-sasl): SMTP with implicit TLS / STARTTLS / AUTH PLAIN, LMTP over tcp or unix socket with per-recipient final responses via `DataCommand.CloseWithLMTPResponse`. **Protocol-level SMTP/LMTP rejections are assertable, not fatal**: go-smtp already turns every 4xx/5xx reply into a `*smtp.SMTPError` (Code + parsed `EnhancedCode` + Message); [internal/provider/mail/client.go](internal/provider/mail/client.go) classifies via `errors.As` — an `SMTPError` becomes a structured `Rejection` (the `Result` carries per-recipient `Rejected` + a transaction-level `Transaction` for mail_from/data/SMTP-final), while transport/IO failures stay fatal errors. `response.json` exposes `accepted` / `rejected` / `stage` (`accepted`/`mail_from`/`rcpt`/`data`/`message`) / `status_code` (number\|null) / `enhanced_status_code` / `message` / `recipients{accepted, rejected[]}` (each rejection: `address, stage, status_code, enhanced_status_code, message`) / `message_id` / `protocol`. `expect { json = {...} }` then decides PASS/FAIL (a rejection with no `expect` is a PASS). The report request map is metadata-only (never the body, attachment bytes, or password). V1 opens a fresh connection per step (no `io.Closer`). The e2e mock ([e2e/mockserver/mail.go](e2e/mockserver/mail.go)) rejects scoped magic targets (`@invalid-sender.test`, `reject@example.test`, header `X-Reject-Message`, LMTP `bad@example.test`) for the rejection scenarios. See [website/src/content/docs/docs/providers/mail.mdx](website/src/content/docs/docs/providers/mail.mdx).
  - `browser/`: Chrome / Chromium UI provider (V1, `target = "<name>"`). Drives Chrome via the Chrome DevTools Protocol (chromedp). Owns per-target sessions: one Chrome subprocess per (target, scenario) pair via `chromedp.NewExecAllocator` + `chromedp.NewContext`, closed via `io.Closer` at suite end. Subpackages: `driver` (transport-agnostic interface + `FakeDriver` for unit tests), `chrome` (production chromedp implementation + Chrome executable locator). Action surface decoded in source order by [internal/parser/browser.go](internal/parser/browser.go): `goto | click | fill | clear | press | submit | scroll | wait_visible | wait_not_visible | hover | select | check | uncheck | reload | back | forward`. Expectations: `visible | not_visible | text | value | enabled | disabled | attribute | url | title`. Inside browser-step `capture`, the runtime injects `text("selector")`, `attribute("selector", "name")`, `browser.url`, `browser.title`, backed by a single post-step `Snapshot` (URL + title + outerHTML) recorded by the provider. Artifacts: `build/artifacts/browser/<scenario>/<step>/<phase>/attempt-N/{step,actions/NNNN-kind-selector}/{screenshot.png,dom.html}`. Capture mode reuses the shared `provider.CaptureMode` (none / failures / steps / actions). Real-browser steps are **not seed-deterministic**; pin flakiness with `retry`, bounded `wait_visible`, and per-action timeouts. `back` / `forward` have known navigation-timing quirks (chromedp.NavigateBack hangs on the CDP response after navigation tears down the JS context); V1 ships a JS history.back() workaround with a 200ms settle delay; prefer explicit `goto` when reliability matters. The CLI registers the provider via [internal/provider/browser/chrome](internal/provider/browser/chrome).New() which wraps `browser.New(WithSessionBuilder(chrome.DefaultBuilder()))`. Set `TALES_BROWSER_DEBUG=1` for verbose stderr traces. See [website/src/content/docs/docs/providers/browser.mdx](website/src/content/docs/docs/providers/browser.mdx).
  - `webhook/`: generic in-memory HTTP receiver (V1, `step "webhook"`). A single `*webhook.Provider` is shared across all scenarios; it owns a `receivers map[string]*receiver` guarded by a mutex and implements `io.Closer` so leftover receivers are torn down at suite end. A step performs **exactly one** of `start` (bind a listener via `net.ListenConfig`, serve in a goroutine, store under a deterministic ID `webhook_<hex>` derived from `DeriveSeed(seed, scenario, step, file, "webhook-id")`; idempotent on retry), `wait` (block until `count` requests arrive or `timeout`/ctx-cancel; assertions run in the runtime, not the provider), or `stop` (shut down + deregister; idempotent). Lock order is always `Provider.mu` → `receiver.mu`; `wait` never holds `Provider.mu` while blocked, and the handler appends under `receiver.mu` then non-blocking-sends on a buffered `signal` channel. [internal/provider/webhook/server.go](internal/provider/webhook/server.go) records each request (method, path, query, first-value `headers` + multi-value `headers_all` with canonical MIME keys, `body{raw,json}`, remote_addr, received_at) and builds the callback URL (`buildWebhookURL`: `public_url` wins, else `public_scheme://(public_host|listen-host):(public_port|listen-port)<path>`). [internal/provider/webhook/signature.go](internal/provider/webhook/signature.go) holds the reusable, exported HMAC helpers (`ParseSignatureFormat`, `ComputeHMAC` for sha1/256/384/512, constant-time `SignaturesEqual`, `TimestampWithinTolerance`) consumed by the runtime. The runtime executor lives in [internal/runtime/webhook.go](internal/runtime/webhook.go): for `start` it injects a `webhook` namespace (id/url/listen_url/address/port/path) into capture; for `wait` it sets `scope.Request` = the received request (so `request.*` works) and `scope.Response` = `{json:{received,count,requests,request}}` (so `response.json.count` works), then runs the custom `expect { request{...} hmac_signature{...} }` assertions reusing `assertion.MatchJSON`. HMAC failures emit a leak-free `Mismatch` (no secret / payload / digest); the report is metadata-only with `diagnostic`-masked headers and never the raw body. See [website/src/content/docs/docs/providers/webhook.mdx](website/src/content/docs/docs/providers/webhook.mdx).
  - `file/`: read-only file inspection (V1, `step "file"`). Stateless `*file.Provider` shared across scenarios. The runtime ([internal/runtime/file.go](internal/runtime/file.go)) resolves the step-level `path` via `workspace.Resolver.ResolveInput`, derives `Need*` flags from the file expect + capture `file.*` refs (`lang.FindFileRefs`), then the provider reports `path`/`exists`/`size_bytes` always and reads hashes/text/json lazily (a missing file is `exists=false`, not an error, unless a read is required; invalid UTF-8 / JSON fail clearly). Assertions reuse `assertion.MatchJSON`; the `file` namespace is injected into capture via `EvalWithExtras`. Report is metadata-only (never text/json content). Parser: [internal/parser/file.go](internal/parser/file.go) (`decodeFileExpect` reads typed `json` + remainder `exists`/`size_bytes`/`text`/`sha*`). See [website/src/content/docs/docs/providers/file.mdx](website/src/content/docs/docs/providers/file.mdx).
  - `exec/`: external command runner (V1, `step "exec"`), **disabled unless `--allow-exec`**. `New(WithAllowExec(bool))` holds an immutable flag (safe across parallel scenarios); `Execute` gates first (`exec provider is disabled by default. Re-run with --allow-exec.`), rejects `docker` mode (`exec sandbox mode "docker" is not implemented yet`), resolves the command (bare→PATH, `./rel`→under `project.dir`, absolute→only within workdir/project.dir via `workspace.Contains`), builds the env (minimal=PATH+TMPDIR+HOME+user / inherit=os.Environ()+user), runs `exec.CommandContext` **directly (no shell)** with the timeout (default 30s), caps each stream at 1 MiB (`cappedBuffer`), and always writes `stdout.txt`/`stderr.txt`/`metadata.json`(+`stdout.json`) under `<scenario.workdir>/exec/<step>/` (metadata never carries env/arg values). The runtime ([internal/runtime/exec.go](internal/runtime/exec.go) + `exec_eval.go`) lowers the step, resolves the sandbox workdir (scenario|project|custom), injects `stdout`/`stderr`/`exec` namespaces for expect+capture, attaches artifacts even on failure, and fails clearly when `stdout_json` is expected but stdout is not JSON. `response`: `exit_code`, `stdout{raw,json,truncated}`, `stderr{raw,truncated}`, `duration_ms`. Parser: [internal/parser/exec.go](internal/parser/exec.go). The `process` sandbox is hygiene, **not** a security boundary. See [website/src/content/docs/docs/providers/exec.mdx](website/src/content/docs/docs/providers/exec.mdx).

## DSL Surface (when editing it)

Execution model: scenarios run in parallel (`--parallel`); **steps inside a scenario run sequentially in `.tales` file order**. A step may reference (`result.<step>`) or `depends_on` only steps defined earlier in the file; forward/unknown references are rejected at load time (`validateScenarioStepOrder` in [internal/parser/loader.go](internal/parser/loader.go), exit code 2). `depends_on` does not reorder steps; it is optional documentation/validation only. The parser preserves the textual order of interleaved `step`/`case` blocks via an `hclsyntax` walk ([internal/parser/order.go](internal/parser/order.go)).

The DSL accepts these top-level blocks: `version`, `config`, `generator "<type>" "<name>"`, `scenario "<name>"`, `keyword "<name>"`. Inside `scenario`: `step "<provider>" "<name>"` (with optional `retry`, `vars`, `request`, `expect`, `capture`, `depends_on`, `when`) and `teardown { step ... }`. The `vars { ... }` block declares step-local variables evaluated **once, in source order, before the provider runs**; later vars can reference earlier ones via `vars.<name>` and the cumulative scope is visible to `request` / `expect` / `capture` of the current step only. Source order is preserved by walking `hclsyntax.Body.Attributes` and sorting by `Range.Start.Byte` in [decodeStepVars](internal/parser/decode.go). Validation in [lang.ValidateStepVars](internal/lang/refs.go) rejects forward refs, self-refs, unknown var consumers, and any `vars.<name>` reference in `when` or skip rules (which are evaluated before the step body). vars are not propagated cross-step; use `capture` to share. Runtime evaluation lives in [evaluateStepVars](internal/runtime/runner.go) and is wired into the HTTP, mobile, and SQL step paths. SQL steps additionally accept `connection = "<name>"` and exactly one of `exec { sql; args }` / `query { sql; args }`: placeholders are driver-dependent (`$1` for Postgres, `?` for MySQL); see [website/src/content/docs/docs/providers/sql.mdx](website/src/content/docs/docs/providers/sql.mdx). Mail steps (`step "mail"`) accept `target = "<name>"` (shared with mobile/browser) plus a `message { ... }` block decoded in [internal/parser/mail.go](internal/parser/mail.go): `from` (required, single sender), `to`/`cc`/`bcc` (lists; at least one recipient required), `subject`, `headers` (map), `text`, `html`, and order-preserving `attachment { filename; content_type?; path | content }` blocks (exactly one of path/content, filename required, at least one of text/html/attachment). The browser dispatcher defers to the mail dispatcher because `target` is shared. Mail reuses the generic `expect { json = {...} }` + `capture` path unchanged. Webhook steps (`step "webhook"`) declare **exactly one** of `start { address?; path (required, must start "/"); public_url?; public_scheme?; public_host?; public_port?; max_body_size? }`, `wait { timeout?; count? }`, or `stop { target }` (decoded in [internal/parser/webhook.go](internal/parser/webhook.go)); `wait` reads the step-level `target = result.<start>.id`, `stop` its own `stop.target`. The browser dispatcher also defers to the webhook dispatcher because `target` is shared. Their `expect` block is webhook-specific (`request { method/path/headers/query/json/body }` and `hmac_signature { header; secret; algorithm?; format; payload; timestamp_tolerance?; timestamp_required? }`, walked from `expect.Remainder` blocks); top-level HTTP expect attributes (`status/json/headers/body/strict`) are rejected on a webhook step. Inside a `wait` step the received request is exposed under the `request` namespace (`request.method/path/query/headers/headers_all/body.raw/body.json/json`) and a summary under `response.json` (`received/count/requests/request`); the HMAC `payload` expression is evaluated with an injected `timestamp` variable. Browser steps share `target` and `actions` with mobile but use CSS selectors (`selector = "..."` instead of `id = "..."`); the parser dispatches mobile-vs-browser per provider label and rejects cross-pollination (e.g. `id` in a browser expect block, or `attribute`/`url`/`title` in a mobile expect). The `actions` schema container ([internal/parser/schema.go](internal/parser/schema.go) `actionsBlock`) is provider-agnostic; each provider walks the body itself via `hclsyntax` to preserve declaration order. `scenario` and `step` additionally accept any number of `skip_if { ... }` / `skip_unless { ... }` blocks; attributes are `condition` (bool expr), `reason` (string), `os` / `arch` / `env_set` (list of strings), and `env` (map of string=>string). Evaluation lives in [internal/runtime/skip.go](internal/runtime/skip.go); skip→dependent cascade in [internal/runtime/tracker.go](internal/runtime/tracker.go); user-facing reference in [website/src/content/docs/docs/writing-scenarios/conditional-execution.mdx](website/src/content/docs/docs/writing-scenarios/conditional-execution.mdx). Mobile steps additionally accept `platform`, `target`, `launch { clear_state }`, `terminate {}`, `permissions { <service> = "allow" | "deny" }` (privacy permissions applied via `simctl privacy` before launch; service names are simctl privacy services: camera, photos, location, contacts, microphone, …), `actions { tap | double_tap | long_press | input_text | clear_text | swipe | scroll | press_key | press_button | set_orientation | dismiss_keyboard | scroll_to | wait_visible | wait_not_visible }` (decoded in source order via `hclsyntax`; every action accepts optional `timeout` and `interval`; `long_press` accepts `duration`; `swipe` / `scroll` accept `direction` (up/down/left/right), optional `distance` (fraction 0–1) and `duration`; the device-level actions take `key` (return/enter/tab/space/escape/delete), `button` (home/lock) or `orientation` (portrait/landscape_left/landscape_right/upside_down) and no `id`; `dismiss_keyboard {}` takes no attributes and dispatches to the Swift driver's `/dismissKeyboard` endpoint which reuses the existing `dismissKeyboardIfPresent` helper (multi-locale Return/Done/Send/... key sweep, fallback tap above the keyboard); `scroll_to { id | label }` takes the same XOR locator as the element-targeted actions and dispatches to the Swift driver's `/scrollTo` endpoint which resolves the element and drags the window via `XCUICoordinate` to bring it into a safe area (top inset 100pt, bottom inset 60pt to clear the keyboard); both branches of the `input_text` handler in Swift (SecureField paste mode AND the regular TextField path) hard-block their respective typing API behind a `focusElementForTextInput` guard that taps + waits for the keyboard, attempts a single `scrollElementIntoView` + retap on miss, and returns a 500 with an actionable error when both fail — this stops the XCTest API violation `Failed to synthesize event: Neither element nor any descendant has keyboard focus` from tearing the runner down on offscreen targets (the original sealway BusinessOnboardingView repro), regardless of whether the field is a `SecureField` or a regular `TextField`; non-paste only runs the guard when an `id` or `label` is provided, preserving the legacy "type into whatever is focused" use case (e.g. after a `press_key` brought up a search bar) when neither locator is set; the resolution helper `resolveLocatorElement(app, id, label)` is shared between the focus guard and the locator-aware paths; `press_key { key = "return" | "enter" }` auto-routes through `app.keyboards.buttons[label].tap()` when a soft keyboard is up (the synth path via `PointerEventPath.pathForTextInput` crashes the XCTest runner on iOS 26.x when a SwiftUI TextField is focused); `/hierarchy` snapshots are scoped to `app.windows.firstMatch.snapshot()` instead of `app.snapshot()` to skip the iOS keyboard daemon's accessibility tree (~hundreds of keys + predictive bar) that would otherwise push a single snapshot past the 8s bounded timeout on tall SwiftUI forms (issue tales-mobile-ios26-form-snapshot-stall.md); falls back to `app.snapshot()` when no window is exposed yet (between terminate and the next launch); every non-/health Swift handler emits a `[tales-driver] request:` + `[tales-driver] response:` NSLog pair around dispatch so the last request before a runner crash is the one that triggered it (the gap between request and response is the hung action); when the runner dies mid-scenario the Go provider detects transport-level failures (`connection refused` / `EOF` / `broken pipe` / `connection reset`) via `looksLikeDriverDeath` and wraps the action error through `wrapDriverDeathError` with the three diagnostic file paths Tales allocated for the session — `apple.DriverDiagnostics{DriverLog, XCResultDir, BuildLog}` returned by `Lifecycle.EnsureDriver`, stored on the `Session.Diagnostics` field, threaded by `default_builder.go`; the same paths are also attached to the step report as `driver_log` / `xcresult_dir` / `driver_build_log` artifacts (merged into `output.Response["artifacts"]` via `appendArtifactsToOutput`) so the visual / JSONL surfaces render clickable links; external drivers (`driver.external = true`) get empty diagnostics because Tales doesn't own their runner; every action that resolves an element by `id` (`tap`, `double_tap`, `long_press`, `input_text`, `clear_text`, `swipe`, `scroll`, `wait_visible`, `wait_not_visible`) accepts an optional `first = true` attribute that routes the resolver through `tree.FindFirstByID` (pre-order first match, XCUITest `firstMatch` semantics) instead of `tree.FindByID` — necessary for iOS system pickers like `PhotosPicker` whose cells share an accessibility id as siblings; the strict default is preserved on `expect { visible | not_visible | text | value | enabled | disabled }` so assertions keep their uniqueness guarantee; every element-targeted action AND every expect block above also accepts `label = "<accessibilityLabel>"` as a mutually-exclusive **alternative** to `id` (parser-enforced XOR; conflicting → `Conflicting element locator`, missing both → `Missing element locator`) — `label` routes through `tree.FindFirstByLabel` on the Go snapshot and triggers a `matching(NSPredicate(format: "label == %@", label)).firstMatch` branch in the Swift driver's `handleTap` / `handleDoubleTap` / `handleLongPress` / `handleInputText` (driver client sends `id = ""` alongside `label = "..."`); indispensable for iOS system controllers whose buttons expose `accessibilityLabel` but no `accessibilityIdentifier` (`PhotosPicker` / `PHPickerViewController` Done, `UIDocumentPickerViewController`, share sheet, `MFMailComposeViewController`, `MFMessageComposeViewController`, most system alerts)), and `expect { visible | not_visible | text | value | enabled | disabled }` blocks (each with `id`, optional `timeout`, `interval`; `text` / `value` accept literal strings or matchers such as `contains(...)` / `matches(...)`). File steps (`step "file"`) take a step-level `path` (required; file-only, rejected on other providers) and a file-specific `expect { exists | size_bytes | text | json | sha1..sha512_256 }` (decoded in [internal/parser/file.go](internal/parser/file.go): typed `json` + remainder attrs; HTTP-style `status/headers/body/strict` rejected). Exec steps (`step "exec"`) take `command` (required), `args`, `env`, `stdin`, `timeout`, and a `sandbox { mode | workdir | env | network }` block, with an exec-specific `expect { exit_code | stdout | stderr | stdout_json }` (decoded in [internal/parser/exec.go](internal/parser/exec.go); the typed HTTP `json` attr is rejected in favor of `stdout_json`). Both, like webhook, return early from `decodeStepExpect` and decode their own expect inside the provider decoder. Any http step may carry a `save { body = "<path>" }` block ([internal/parser/save.go](internal/parser/save.go)); it is rejected on non-http providers. Backward-compatible aliases (`case` for `step`, `response` for `expect`) are decoded in [internal/parser/schema.go](internal/parser/schema.go) and must keep working, but they are now **deprecated** and emit a load-time warning (see the `deprecation.go` note in the parser bullet above).

For mobile iOS targets, the `driver` block resolves to one of three modes: **embedded** (default, omit `source_path`), **developer override** (`source_path = "..."`), or **external** (`external = true`, only health-checks the URL). The legacy `project` + `scheme` fields are no longer accepted and produce a parse error pointing at the migration. See [website/src/content/docs/docs/providers/mobile-ios.mdx](website/src/content/docs/docs/providers/mobile-ios.mdx) for details.

A `scenario { record { output = "<path>"; codec?; mask?; display?; target?; force? } }` block (decoded in [internal/parser/record.go](internal/parser/record.go)) records the main steps of the scenario via simctl. The block is provider-agnostic on the parser side but only honored by the mobile iOS provider in V1 through the new `provider.ScenarioHook` capability ([internal/provider/scenario_hook.go](internal/provider/scenario_hook.go)) that the runner type-asserts on every registered provider, same pattern as `io.Closer` at suite end. The hook's `BeginScenario` resolves output paths via the existing `workspace.Resolver` (no traversal out of `scenario.workdir`) and stores a pending spec; the recorder is started lazily on the first mobile `acquireSession` and stopped by SIGINT **between the last main step and the first teardown step** (`endHooks()` is called explicitly in [internal/runtime/runner.go](internal/runtime/runner.go) and again via defer as a panic safety net, with idempotence), so a teardown step can assert on the finalized file and the recording does not cover the `terminate {}` cleanup. Artifacts are surfaced as `ScenarioResult.Artifacts` (type `"recording"`) in console, JSONL (`scenario.artifacts[]`), JUnit (`<system-out>`), and the visual report JSON model. The opt-in pattern is `skip_unless { env_set = ["TALES_RECORD"] }` plus a tag, no new CLI flag.

The `tales doctor` subcommand ([internal/cli/doctor.go](internal/cli/doctor.go)) is the one-stop diagnostic: Tales build info, embedded driver source hash, cache enumeration via [internal/provider/mobile/apple/embeddeddriver/inspect.go](internal/provider/mobile/apple/embeddeddriver/inspect.go), and Xcode/simctl probes. `--json` makes it scriptable from CI. `make doctor-ios` remains as a shell-only fallback when the Tales binary is unavailable.

Available generator types: `email`, `password`, `timezone`, `locale`, `person`, `mac_address`, `bytes`, `date`, `datetime`, `unix_time`. The last three are deterministic, seed-replayable date/time generators in [internal/runtime/generator.go](internal/runtime/generator.go) (`runDateGenerator` / `runDateTimeGenerator` / `runUnixTimeGenerator`, backed by go-faker's `Date`/`DateTime`/`UnixTime` via the existing seeded `generatorRandom.faker()` path): each takes required inclusive UTC `from`/`to` bounds, parsed via the shared `dateRangeFromParams` (`date` uses `YYYY-MM-DD`, `datetime`/`unix_time` use RFC3339); `date` returns a `YYYY-MM-DD` string, `datetime` an RFC3339 UTC string (`Z`), `unix_time` a **number** (int64 seconds). They are distinct from the intentionally non-deterministic `now_unix`/`now_rfc3339` wall-clock functions. Available matchers/functions: `env`, `generate`, `jsonencode`, `url_encode`, `base64url_encode`, `now_unix`, `now_rfc3339`, `sha1_hex`, `sha224_hex`, `sha256_hex`, `sha384_hex`, `sha512_hex`, `sha512_224_hex`, `sha512_256_hex`, `hmac_sha1_hex`, `hmac_sha224_hex`, `hmac_sha256_hex`, `hmac_sha384_hex`, `hmac_sha512_hex`, `hmac_sha512_224_hex`, `hmac_sha512_256_hex`, `pkce_challenge`, `totp`, `regex_find`, `contains`, `matches`, `exists`, `not_exists`, `is_string`, `is_number`, `is_bool`, `is_array`, `is_object`, `one_of`, `uuid`, `can`, `optional`, `required`, `any`, `lt`, `lte`, `gt`, `gte`, `between`. The hash and HMAC variants live in [internal/lang/hash.go](internal/lang/hash.go) and [internal/lang/hmac.go](internal/lang/hmac.go); both files share a single helper so adding a new algorithm is one map entry. `jsonencode` produces a canonical JSON string (object keys sorted alphabetically, sets sorted by encoded form, numbers preserved via `json.Number`). The determinism is load-bearing for any signing scheme. `now_unix` / `now_rfc3339` read the wall clock and are intentionally non-deterministic; capture them in a step-local `vars` block when stability is required. Every HMAC and hash function returns lowercase hex and never embeds the secret/message in error messages. `base64url_encode(value)` returns RFC 4648 URL-safe Base64 of the input string bytes without padding; it does **not** decode hex, so `base64url_encode(sha256_hex(verifier))` is not a valid PKCE S256 challenge; use `pkce_challenge(verifier)` ([internal/lang/pkce.go](internal/lang/pkce.go)) which encodes the raw 32 SHA-256 bytes per RFC 7636. `pkce_challenge` accepts `{method = "S256"\|"plain"}`; unknown options/methods are rejected. The `code_verifier` JSON field name is masked by [internal/diagnostic/diagnostic.go](internal/diagnostic/diagnostic.go). `totp(secret_base32, options?)` implements RFC 6238 on top of `hmac_sha1_hex`; defaults are `period=30, digits=6, algorithm="SHA1", timestamp=now_unix()`. Options must be an object: unknown keys, unsupported algorithms (anything other than `"SHA1"` in V1), or out-of-range `digits`/`period`/`timestamp` are rejected at evaluation time. The secret is opaque in errors; invalid Base32 always surfaces as `invalid TOTP base32 secret`. The `uuid([version])` value matcher asserts an RFC 9562 (ex-RFC 4122) UUID string: the [internal/lang/functions.go](internal/lang/functions.go) factory normalizes/validates the version token at evaluation time (`"v1"`..`"v8"`, the bare digit `"4"`, `"nil"`, `"max"`; an unknown token or more than one argument errors), and [internal/assertion/uuid.go](internal/assertion/uuid.go) (`matchUUID`, registered in `matcherHandlers`) validates the actual value against the canonical hyphenated `8-4-4-4-12` form (case-insensitive), enforcing both the version nibble and the RFC variant (`10xx`). `uuid()` accepts any official UUID (versions 1-8 with valid variant, plus the nil and max UUIDs). Validation is in-house (regexp + nibble checks), no new dependency. Available top-level expression variables: `config`, `result`, `request`, `response`, `input`, `vars` (step-scoped, see vars block above), `host` (with `host.os` = `runtime.GOOS`, `host.arch` = `runtime.GOARCH`), `scenario` (`scenario.workdir` / `scenario.artifacts_dir` / `scenario.name`) and `project` (`project.dir`). The HTTP `save` block adds `response.download` (`path`/`size_bytes`/`sha*`); the file provider injects a `file` namespace into capture; the exec provider injects `stdout`/`stderr`/`exec` namespaces into expect+capture. The HTTP `response` namespace exposes `status`, `json`, `body`, `headers` (map of `list(string)`, every value preserved in wire order, keyed by the canonical MIME name; single-valued headers are returned as a one-element list so users always index with `[0]`, and Set-Cookie / WWW-Authenticate / etc. carry every value), and `cookies` (map of parsed cookie objects with `name`, `value`, `raw`, `path`, `domain`, `expires`, `max_age`, `secure`, `http_only`, `same_site`; duplicate cookie names use the last-seen value). Mobile capture exposes two extra functions, `value("id")` and `text("id")`, injected by the runtime into the EvalContext for mobile steps; they close over the hierarchy recorded for the step. The README and the `tales-test-generator` skill carry the user-facing reference; keep all three in sync when adding to this list.

`optional(value)` and `required(value)` are field-level JSON matchers, handled by [internal/assertion/json.go](internal/assertion/json.go): `optional` lets the key be absent (otherwise the inner value is matched), `required` is the default behavior made explicit and fails when the key is absent. `any()` is a value-level matcher that accepts any present value (`null` included); pair it with `optional(any())` to also allow the key to be missing.

`lt`, `lte`, `gt`, `gte`, and `between` are numeric threshold matchers handled by [internal/assertion/threshold.go](internal/assertion/threshold.go). Their factories live in [internal/lang/threshold.go](internal/lang/threshold.go). Arguments accept either numbers or Go duration strings (`"200ms"`, `"2.5s"`, `"1m"`); duration thresholds are normalised to milliseconds at match time so a metric exposed in an `_ms` field compares directly against a duration. Invalid threshold types and `between(min, max)` with `min > max` are rejected at HCL evaluation time, not at match time.

The browser provider exposes a web performance snapshot under `browser.performance` (and asserts it via `expect { web_perf { … } }`). A script installed via `Page.addScriptToEvaluateOnNewDocument` in [internal/provider/browser/chrome/performance.go](internal/provider/browser/chrome/performance.go) attaches `PerformanceObserver`s for `largest-contentful-paint` and `layout-shift` before the first navigation, then `chromedpDriver.Performance` combines those observer values with `navigation` / `paint` / `resource` entries into `driver.PerformanceMetrics`. The runtime exposes the metrics via [internal/runtime/browser_capture.go](internal/runtime/browser_capture.go) (`browser.performance` namespace) and the parser maps friendly aliases (`fcp`, `lcp`, `dom_content_loaded`, …) to the canonical metric names in [internal/parser/web_perf.go](internal/parser/web_perf.go).

The `load` provider ([internal/provider/load/](internal/provider/load/)) drives one HTTP request concurrently for a `duration` or fixed `requests` count and reports latency percentiles (nearest-rank), RPS, error and status-class ratios. The decoder lives in [internal/parser/load.go](internal/parser/load.go); the step uses an `http { … }` sub-block instead of the top-level `request { … }` so the surface stays distinct from the regular HTTP provider, and an `expect` block accepts flat shortcut attributes (`p95`, `rps`, `error_ratio`, `status_2xx_ratio`, …) walked from `expectBlock.Remainder`. Non-load providers reject the same remainder via `validateExpectExtras`. The runner exports `httpprovider.BuildRequestTemplate` ([internal/provider/http/build.go](internal/provider/http/build.go)) so request construction is shared with the standard HTTP provider; multipart bodies are rejected for load in V1. The runtime wires the load dispatch through [internal/runtime/load.go](internal/runtime/load.go) and surfaces the shortcut assertions via `assertExpectedShortcuts` in [internal/runtime/runner.go](internal/runtime/runner.go). The console reporter prints a compact load recap below the step PASS line via [internal/report/load_summary.go](internal/report/load_summary.go). The end-to-end smoke scenario at [e2e/load/healthz.tales](e2e/load/healthz.tales) is exercised by `make e2e-load` (local only, not wired into GitHub Actions).

## Conventions

- `golangci-lint` v2 config: notable enabled linters include `wsl_v5`, `nlreturn`, `wrapcheck`, `gocyclo` (min-complexity 18), `forcetypeassert`. Run `make lint` before sending changes; CI uses golangci-lint-action v9 with version `v2.10.1`.
- Tests use `-race -count=1`. Avoid time-based flakes: the runtime's retry/scheduler code paths are exercised under race.
- Determinism is a load-bearing property: never introduce wall-clock or `rand` calls in generators/runner without threading the existing seed mixer in [internal/runtime/seed.go](internal/runtime/seed.go).

## Working Rules (mandatory)

### Language

- Always reply to the user in **French**.
- All code, comments, identifiers, commit messages, and documentation must be in **English**.

### Testing

- Every new feature MUST ship with both:
  - **Unit tests** in the relevant `internal/...` package (`*_test.go` with `-race`).
  - **Functional tests** as `.tales` scenarios under `e2e/pass/` (and `e2e/fail/` when the feature has an error path worth pinning).
- Run `make test` and `make e2e` after each feature: do not declare a task done until both pass.
- Follow **TDD for bug fixes**: first write a failing unit or `.tales` test that reproduces the bug, confirm it fails for the right reason, then implement the fix and re-run the test to prove it passes.

### Linting

- Code must pass `make lint` (golangci-lint v2 config). Do not commit lint-dirty code.
- Never silence linters with `//nolint:...` directives. The only acceptable exception is a confirmed false positive, and it MUST carry an inline justification, e.g.:
  ```go
  //nolint:gosec // G404: deterministic seed required for reproducible test data, not a security primitive
  ```

### Docs and skill sync

User-facing docs now live in [website/src/content/docs/docs/](website/src/content/docs/docs/) (Astro + Starlight, published at https://taleslabs.org/). The legacy `docs/` folder has been removed.

When changing the DSL, CLI flags, generators, matchers, or any user-facing behavior, update **all of these** in the same change:

- [README.md](README.md): short summary + link to the website.
- [website/src/content/docs/docs/](website/src/content/docs/docs/): the relevant MDX page (provider / reference / guide / operations).
- [.claude/skills/tales-test-generator/SKILL.md](.claude/skills/tales-test-generator/SKILL.md) (and its `references/`).
- [CLAUDE.md](CLAUDE.md) if the architecture or conventions section is affected.

### Git workflow

- **Commit at every step** of the work: one logical change per commit, not one big terminal commit.
- Commit messages MUST use Conventional Commits prefixes: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`, `build:`, `ci:`, `perf:`, `style:`.
- Write **detailed** commit bodies when the change is non-trivial: what changed, why, and any user-visible impact. Subject stays under ~70 chars; details go in the body.
- **Never push.** The user pushes manually after review. Do not run `git push` (or `gh pr create`) unless explicitly asked in the current turn.
