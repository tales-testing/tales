The JSONL reporter writes one JSON object per line, a complete event stream of the run. It is the richest of the four reporters: every step and every UI action carries its full request, response, and timing data.

## Usage

```bash
tales test ./e2e/pass --report-jsonl ./reports/events.jsonl
```

The file is written after the suite completes (not incrementally). The parent directory is created if missing.

## Event types

Each line carries a `type` field. There are three:

| `type`     | Emitted when                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------- |
| `scenario` | Once per scenario, summarising its final status, duration, and (when failed/skipped) error / skip reason. |
| `step`     | Once per step. Includes a `phase` field set to `"step"` for main-flow steps, `"teardown"` for scenario teardown steps and `"suite_teardown"` for the suite-level teardown block. Retried steps surface their attempt count via `attempts`. |
| `action`   | Once per UI action for mobile and browser steps that recorded actions. Emitted immediately after the parent `step` event. |

There is no separate `suite_start` / `suite_end` envelope. Scenario aggregation is up to the consumer (`jq -s 'group_by(.scenario)'` or similar).

## Example

```jsonl
{"type":"scenario","scenario":"Create blog post","file":"e2e/pass/blog.tales","status":"pass","duration_ms":842,"seed":1234}
{"type":"step","phase":"step","scenario":"Create blog post","step":"create_user","provider":"http","status":"pass","status_code":201,"duration_ms":312,"seed":1234,"file":"e2e/pass/blog.tales","request":{"method":"POST","url":"http://localhost:1337/users"},"response":{"status_code":201,"json":{"id":"u_abc"}}}
{"type":"step","phase":"step","scenario":"Create blog post","step":"create_post","provider":"http","status":"pass","status_code":201,"duration_ms":418,"seed":1234,"file":"e2e/pass/blog.tales"}
{"type":"step","phase":"teardown","scenario":"Create blog post","step":"delete_user","provider":"http","status":"pass","status_code":204,"duration_ms":112,"seed":1234,"file":"e2e/pass/blog.tales"}
{"type":"step","phase":"suite_teardown","scenario":"tales:suite-teardown","step":"purge_test_users","provider":"sql","status":"pass","duration_ms":9,"seed":1234,"file":"e2e/pass/_suite.tales"}
```

The order is `scenario` event first, then its `step` events (main flow, then teardown) interleaved with any `action` events.

The suite-level teardown runs after every scenario, so its `suite_teardown` events come last in the stream. They carry the reserved scenario name `tales:suite-teardown`.

## Fields you can rely on

### `scenario` event

| Field         | Type     | Notes                                                       |
| ------------- | -------- | ----------------------------------------------------------- |
| `type`        | string   | Always `"scenario"`.                                        |
| `scenario`    | string   | Scenario name.                                              |
| `file`        | string   | Path to the `.tales` file that defines the scenario.        |
| `status`      | string   | `pass`, `fail`, `skipped`.                                  |
| `duration_ms` | number   | End-to-end wall-clock duration of the scenario.             |
| `seed`        | number   | The `--seed` value used for this run.                       |
| `error`       | object   | When failed: kind, path, want, got, message.                |
| `skip_reason` | string   | Present only when `status="skipped"`. Omitted otherwise.    |

### `step` event

| Field         | Type     | Notes                                                            |
| ------------- | -------- | ---------------------------------------------------------------- |
| `type`        | string   | Always `"step"`.                                                 |
| `phase`       | string   | `"step"`, `"teardown"` or `"suite_teardown"`.                    |
| `scenario`    | string   | Scenario name.                                                   |
| `step`        | string   | Step name.                                                       |
| `provider`    | string   | `http`, `sql`, `mobile`, `browser`, `keyword`, ...               |
| `status`      | string   | `pass`, `fail`, `skipped`.                                       |
| `duration_ms` | number   | Step duration including retries.                                 |
| `seed`        | number   | The `--seed` value used for this run.                            |
| `file`        | string   | Path to the `.tales` file that defines the step.                 |
| `status_code` | number   | HTTP status code, when applicable. Omitted for non-HTTP steps.   |
| `attempts`    | number   | Total attempts run, present only when greater than 1 (the step retried). A single-attempt step omits the field entirely. |
| `skip_reason` | string   | Present only when `status="skipped"`. Omitted otherwise.         |
| `request`     | object   | Provider-specific request shape. Omitted when empty.             |
| `response`    | object   | Provider-specific response shape. Omitted when empty.            |
| `actions`     | array    | Mobile: per-action records, mirrored at the request level.       |
| `artifacts`   | array    | `{type, path}` of the files the step produced, omitted when empty. Mobile: `screenshot`, `hierarchy`, `logcat`, driver logs. Browser: `screenshot`, `dom`, and the [failure diagnostics](/docs/providers/browser/#failure-diagnostics) `console`, `network`, `state`. |
| `error`       | object   | When failed: kind, path, want, got, message.                     |

### `action` event

One per UI action of a mobile or browser step, emitted after the step event when `step.actions` is populated. Empty action arrays produce byte-identical JSONL to the pre-action-stream format, so legacy consumers keep working.

```json
{
  "type": "action",
  "scenario": "iOS register",
  "step": "fill_form",
  "index": 0,
  "kind": "input_text",
  "label": "register.email",
  "value": "qa@example.com",
  "status": "pass",
  "duration_ms": 42,
  "started_at": "2026-10-21T08:14:22.339Z",
  "ended_at": "2026-10-21T08:14:22.381Z",
  "screenshot": "build/artifacts/mobile/.../screenshot.png",
  "hierarchy":  "build/artifacts/mobile/.../hierarchy.json"
}
```

| Field         | Type   | Notes                                                                                                                         |
| ------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `started_at`  | string | When the action started, UTC with millisecond precision (`2026-10-21T08:14:22.339Z`). Absent on a skipped action, which never ran. |
| `ended_at`    | string | When the action finished (`started_at` plus its duration). Absent on a skipped action.                                       |
| `point`       | object | Browser pointer actions (`click`, `hover`, `check`, `uncheck`): `{"x": 84.5, "y": 90.4}`, where the mouse events were sent, in CSS pixels from the viewport's top-left corner. When the action failed its actionability checks, the point its last check tested. Absent otherwise. |

`started_at` and `ended_at` use the same layout as the `time` of a browser step's `console.jsonl` and `network.jsonl`, so the strings sort and compare across files: a failed click can be lined up with what the page logged and sent around it.

Secure values are masked to `"***"` at one boundary inside the mobile and browser providers, see [Visual HTML report](/docs/reports/visual/#secure-values).

A browser action whose screenshot or DOM capture had to be skipped also carries `capture_note`, a short sentence saying why (for example `"screenshot skipped: the page kept navigating while it was captured"`). The field is absent when the capture is complete. See [Browser provider](/docs/providers/browser/#captures-never-hold-the-run).

## DSN and secret masking

The SQL provider scrubs DSNs from every event before serialisation. Only the connection name, driver alias, SQL text, and arg *count* appear, never the connection string. See [SQL provider](/docs/providers/sql/#security-and-masking) for the full rules.

`auth.basic.password` is masked in HTTP request shapes. Other secrets injected via `headers` are not masked, capture them from upstream responses if you need masking.

## Consuming the stream

### With `jq`

```bash
# Count failures
jq -c 'select(.type=="step" and .status=="fail")' events.jsonl | wc -l

# All failure messages with their step path
jq -c 'select(.type=="step" and .status=="fail") | {scenario, step, msg:.failure.message}' events.jsonl

# Total wall-clock time across scenarios (parallelism aware)
jq -s 'map(select(.type=="scenario") | .duration_ms) | add' events.jsonl

# All retried steps with their attempt count
jq -c 'select(.type=="step" and .attempts) | {scenario, step, attempts}' events.jsonl
```

### In a log pipeline

JSONL plays nicely with Loki, Elasticsearch, BigQuery, Snowflake, Datadog logs. Ingest the file once at suite end and query at will.

<Aside type="tip" title="Pair JSONL with the visual report">
	JSONL is the system-of-record. The [visual HTML report](/docs/reports/visual/) is the UX layer that makes mobile timelines clickable. They share the same underlying data, so anything you can see in the HTML can be queried with `jq` against the JSONL.
</Aside>
